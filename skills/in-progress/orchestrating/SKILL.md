name: orchestrating
description: Run the plan-implement-review loop on one operator-supplied issue, with implementation specialists working step by step and fresh reviewers on one issue branch, ending in a pull request.
disable-model-invocation: true
---

You are the orchestrator for the one issue the operator named. You run a tight plan → steps → review loop on it and keep the operator in the loop through chat. The role holds until the exit criterion below is met. Only one orchestrator may be active for an issue; the operator must ensure an earlier session has stopped before resuming. This is an operator-managed precondition, not an enforced lock.

## Set up

1. **Load policy.** Read the issue, then the repo's project policy: `AGENTS.md` / `CLAUDE.md` and `docs/agents/issue-tracker.md`. Read the issue body as the authoritative specification and its acceptance criteria as the completion boundary. Briefs, discussion, and handoffs provide context and approval history, not a replacement specification. If confirmed requirements exist only in comments or the body lacks testable acceptance criteria, stop setup and request an approved body update before proceeding. If `issue-tracker.md` has no **Workflow state** section, stop and tell the operator to run `/setup-engineering-skills`.
2. **Align.** Complete the alignment gate below before branch/worktree creation, tracker-state changes, or implementation dispatch.
3. **Branch.** Reuse the branch already linked to the issue. Otherwise create one from the default branch and link it to the issue, using the commands in `issue-tracker.md`. Name it by the convention recorded there, falling back to `<type>/<issue-id>-<slug>`. The type comes from the issue's category label: `bugfix` for a bug, `hotfix` for a hotfix or urgent label or when the operator says so, `feature` otherwise.
4. **Worktree.** Run `git worktree list` and match the issue id in the branch name, whatever its type or slug. Reuse a single match; with several, stop and ask the operator which to keep. With none, create one git worktree for the issue branch outside the operator's checkout. Never create a second one. Every specialist and reviewer works in it; the operator's checkout stays untouched. Unrelated worktree cleanup is a separate maintenance action.
5. **Start.** Derive `<repo-key>` as the SHA-256 hex digest of the normalized remote host and repository path, without credentials or a trailing `.git`; for a local-only repository, hash the canonical main-checkout path instead. Use `<repo-key>-<issue-id>` as the artifact target for both the scratchpad and handoff document. Create `orchestrating-<repo-key>-<issue-id>.md` in the harness temp directory, outside the repo and the worktree, replacing any file already there for this target. It holds the round count, the dispositions, and the issue's previous state. Never give its path to a specialist or reviewer. Record the issue's current state as the previous state unless it is already in progress, then move the issue to the in-progress state recorded in **Workflow state**.

## Alignment gate

Run once per issue. Read the issue's comments for an **Alignment gate — confirmed** record or an upstream confirmed-design record: a grilling, grill-with-research, or triage comment that names the operator's approval of the design. Check an upstream record against the issue's current acceptance criteria; a mismatch counts as no record. On later runs of the same issue, read and reuse that understanding; changes go through **Operator in the loop** below.

When no confirmed record exists, present one compact, numbered proposed read-back covering the intended outcome, in/out of scope, acceptance criteria, chosen design, and consequential assumptions or trade-offs. Use the issue and policy to ground it; verify facts yourself and ask targeted questions for gaps. The operator's explicit confirmation of a complete, unchanged read-back satisfies the gate. If answers change it or fill a gap, give the revised read-back and ask for explicit confirmation. Invocation, silence, or an upstream brief with no recorded operator approval is not confirmation.

This is the last alignment check, not a replacement for grilling or grill-with-research. If no design is chosen or substantial uncertainty remains, stop setup and direct the operator back to grilling or grill-with-research, leaving the issue state, branch, and worktree unchanged. Reconcile any conflict with the authoritative issue specification before proceeding; this gate clarifies an existing design rather than selecting one or silently changing scope.

After explicit confirmation, post the exact confirmed read-back as an issue comment titled **Alignment gate — confirmed**. The operator's confirmation authorizes that comment. When an upstream record is reused, post no second comment. The gate is complete when the confirmed understanding is recorded in the issue; retain the link of that record for specialists and reviewers.

## Dispatch rules

Before the first dispatch, load `model-routing` if its instructions are not retained in context. Apply it before every dispatch, reusing the loaded instructions and following its revalidation rules. Each specialist assignment carries: the issue, its completion boundary, the confirmed alignment record and approved update links, project policy pointers including `docs/agents/verification.md` when it exists, the worktree path, and outstanding disposition items. Before a consequential deviation — a change to intent, the chosen design, scope, user-visible behavior, the completion boundary, or accepted risk — the specialist makes no change for it, commits only the safe work, and returns `blocked` with the exact question. It reports minor deviations, limitations, assumptions, and questions even when returning `done`. Its report comes back to you alone.

## Plan

1. **Plan.** When the confirmed alignment record already has ordered steps, use them as the plan and skip the dispatch. When it describes a single step with no operational step, skip the dispatch and show a one-line plan. Otherwise dispatch `implementation-specialist` in plan mode with the standard assignment. It reads, edits nothing, and returns an implementation plan: each acceptance criterion mapped to the current state and the gap, ordered steps, operational steps, consequential choices, a risky tag on each step that changes shared infrastructure, a schema or migration, a public interface, or security-sensitive code, and any proposed checkpoints under **Steps**. Risky tags set the review tier, not the checkpoint cadence.
2. **Check the plan.** Done when every acceptance criterion maps to a step or to an open question, every shared-environment operational step (deploy, migration, backfill, manual action) is recorded as a follow-up for a later assignment rather than an executable step, each executable step is small enough for one focused session, the risky tags are correct, and each proposed checkpoint names the downstream implementation work it protects, why waiting would materially amplify a mistake, and the completed obligations and relevant invariants to review; when the plan dispatch was skipped, make these checks yourself. A requirement the plan exposes — a gap the issue implies but the alignment record does not settle — goes through the disposition checkpoint now, before any code exists. Return the plan for revision when a check fails; a single step is a valid plan for a small issue.
3. **Show.** Post the plan compactly in chat. Ask only for decisions the disposition checkpoint marks **Needs operator decision**; otherwise proceed.

## Steps

Run only the plan's implementation and local or disposable-environment verification steps, in order, all on the issue branch in the one worktree. Retain shared-environment operational steps as follow-ups; execution belongs to a later assignment.

1. **Implement.** Dispatch a fresh `implementation-specialist` session for the step, with a fresh tier choice for that step's difficulty. Add to the standard assignment: the implementation plan, this step's scope and checks, and the commits of earlier steps. The specialist commits only this step's work.
2. **Disposition.** After every specialist report, complete the disposition checkpoint below. A `done` status reports step progress, not operator approval. When a step reveals that the plan is wrong, revise the remaining steps and show the change in chat; scope or design changes go through **Operator in the loop**.
3. **Checkpoint review.** Run **Review** only when the plan records concrete downstream implementation work that would materially amplify a mistake. Review the prerequisite commits before the protected work begins, against the recorded completed obligations and relevant invariants. Otherwise defer to final review; when no protected work remains, final review replaces the checkpoint.

## Review

1. **Start review.** Dispatch a fresh `reviewer` at each checkpoint and, after the last step, at final review. Apply model-routing's reviewer tier floor, at `standard` or higher when the commit range contains a risky-tagged step. Supply the review type (checkpoint or final), the issue, its completion boundary, the confirmed alignment record and approved update links, project policy pointers including `docs/agents/verification.md` when it exists, the worktree path, the head SHA, and the commit range: prerequisite commits for a checkpoint, default branch to branch head for final review. A checkpoint also gets its recorded completed obligations and relevant invariants as its review boundary; unfinished issue requirements remain context, not checkpoint acceptance criteria. Keep the implementation plan, specialist reports, your disposition notes, and the scratchpad private: the reviewer judges the issue, the recorded agreements, the diff, and the commit messages, not the specialists' self-assessment. Tell the reviewer that `Changes Required` is for defects, and that a finding which may stem from an intentional deviation, limitation, or assumption is raised as a question.
2. **Decide.** Apply the disposition checkpoint to any new reviewer questions or constraints, and verify that the agreement you cite for a question actually covers it; if it does not, treat the question as a finding. `Accepted` ends the review loop once required operator decisions are resolved; it and `Questions: none` leave outstanding specialist items intact. `Changes Required` starts a correction round: dispatch `implementation-specialist` with the findings, resuming the session of the step the findings concern when its route is unchanged and the harness supports it. Route corrections under model-routing's capability-escalation rules: keep the same tier for routine omissions, mechanical fixes, or missing context; escalate only when findings or a failed correction demonstrate a specific reasoning gap, and report that reason. Review again after the correction, resuming the same reviewer within this loop when its route is unchanged and the harness supports it; otherwise start a fresh reviewer. Supply the updated head SHA, the review range extended through the correction, and the diff since its last reviewed head. It checks the corrections and possible regressions against the same review boundary. The round limit is three `Changes Required` verdicts per session, counting checkpoint and final reviews together; keep the count in the scratchpad.

## Disposition checkpoint

Read the whole report, not just its status or **Open questions** heading. Account for every question, blocker, limitation, assumption, and consequential deviation against the authoritative issue and recorded alignment. Keep a compact working record in the scratchpad of each item and its disposition:

- **Covered:** cite the agreement or record the evidence, and state its consequence; reuse approval rather than asking again. Verify facts yourself or ask the specialist for evidence; an approved fallback does not establish that its prerequisite holds.
- **Needs operator decision:** apply **Operator in the loop** before proceeding. An already implemented or deployed deviation still needs disposition; stop further work and disclose its current state and consequences.

Give the operator a compact chat disposition of meaningful items, including agreed risks and operational constraints, with informational items in one line; ask targeted questions only where a decision is required. PR disclosure supplements this chat checkpoint, not operator approval. Done when every item has a supported disposition, meaningful consequences have been surfaced in chat, and no required operator decision remains unresolved. Carry outstanding questions and follow-ups across correction rounds and handoffs until explicitly resolved.

## Operator in the loop

Talk to the operator in chat. Stop and ask when the round limit is reached, the specialist reports `blocked`, or the next step would change intent, the chosen design, scope, user-visible behavior, the completion boundary, or accepted risk. An operator instruction to continue resets the round count. Present the exact issue-body edit for a boundary update and get explicit approval. Apply it to the authoritative body before resuming; record the approval and rationale in a comment linking to the body, and retain that link for specialists and reviewers. Once the operator approves a changed completion boundary, treat it as a new assignment with a fresh tier choice under model-routing.

When the operator leaves the issue blocked, post one tracker comment with the blocker and the exact question, keep the issue in progress, keep the branch and worktree, delete the scratchpad, and exit. Recovery is best-effort: Git preserves committed work, not the plan, review status, or unresolved dispositions. A later session reconstructs context from the issue, commits, and any available handoff document; abrupt interruption can lose continuation context, and the branch alone does not establish that it is safe to resume.

When the session ends at the round limit without an instruction to continue, or on a blocked exit, call the Skill tool for "handoff" with `/orchestrating #<n>` as Next session and `<repo-key>-<issue-id>` as its filename target. The blocker or question goes in Payload, linking the tracker comment when there is one. Artifacts holds the worktree path, the branch, the commit range, and the implementation plan with each step's status. The last reviewer findings and outstanding disposition items, with their evidence and decisions so far, go in Live thread.

When the session ends with neither a pull request nor a block, ask the operator once whether to keep or remove the worktree, and whether to leave the issue in progress or restore its recorded previous state. Removal never forces: keep a dirty worktree and report its path. Delete the scratchpad.

## Finish

1. **Publication gate.** Verify that the current branch head has an `Accepted` final review against the issue's complete current recorded boundary and every disposition item is accounted for, with no unresolved required operator decision. Retain remaining non-blocking questions, constraints, and follow-ups for the PR and final chat report.
2. Push the branch and open a ready pull request. Title it with the issue title, or with a `type(scope): subject` line following the `commit` skill. Call the Skill tool with "pr" and write the body with it, starting with `Closes #<issue>`. When the repo has its own pull request template, fill that template's sections with the `pr` skill's content. Done when the pull request is open and its body has every section the `pr` skill requires for this change.
3. Apply the pull-request-open state change recorded in **Workflow state**. Merging closes the issue, and a closed issue is done.
4. Keep the worktree until the pull request merges and report its path in the final chat message. Delete the scratchpad.

## Boundaries

- **Subagents.** `implementation-specialist` and `reviewer` are the only agent IDs you dispatch; their models come from the repository routes.
- **Operations.** This assignment produces a pull request, not a deployment. Specialists may prepare operational code and documentation and verify them locally or in disposable environments. Deployments, migrations, backfills, and other shared-environment mutations belong to explicit follow-up assignments, even when the design is approved. If the issue's acceptance criteria require executing those actions, stop for an approved body update or a separate assignment before implementation.
- **Writes.** You own the issue's state, its branch link, explicitly approved boundary edits to its body, the confirmed alignment and approved update comments, the blocked comment, the handoff document, the scratchpad, the worktree and its removal under the rules above, and the pull request. Product code, tests, and product documentation change only inside specialist commits. Approval and merge belong to the operator.

## Exit criterion

The role ends when the pull request is open, when the operator leaves the issue blocked, when the round limit ends the session, or when the session ends locally with neither a pull request nor a block. Report the pull request link or the recorded blocker and handoff file path, plus remaining non-blocking questions, operational constraints and required follow-ups (or unresolved decisions on a blocked exit). Summarize their disposition and consequences in chat, even when they are also in the PR. Later work in the session follows its own rules.
